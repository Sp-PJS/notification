## 💡 요구사항 해석 및 가정

### 1. Java VS Kotlin

- **Kotlin**은 **가독성이** 높고, **Null-Safety**하며, **코루틴(Coroutine)**을 통한 비동기 처리가 강력하다는 장점
- **Java**는 가장 거대한 커뮤니티와 레퍼런스를 보유

→ 트러블슈팅을 할 때 Java의 래퍼런스가 많으므로 안정적인 개발을 위해 **Java 선택**

### 2. JPA VS MyBatis

- **MyBatis**는 SQL 중심의 매퍼(Mapper) 프레임워크로 **SQL을 직접 제어(XML)**하므로 **복잡한 통계 쿼리나 대량 통계성 데이터 처리**에 유리
- JPA(Hibernate)는 객체와 데이터베이스를 **매핑(ORM)**해 주어, SQL 중심이 아닌 '도메인/비즈니스 로직' 중심으로 개발 가능

→ 알림 자체의 **상태(구현 범위 2. 알림 처리 상태 관리 내용 참조)**가 자주 바뀌므로 **JPA 선택(변경 감지(Dirty Checking))**

### 3. MySQL vs PostgreSQL

- **PostgreSQL**은 **JSON 구조(NoSQL 대용) 처리나 복잡한 조인, 격리 수준(Isolation Level) 처리**가 매우 정교하므로 기능적으로는 MySQL보다 무겁고 강력함
- **MySQL**은 동시 쓰기/읽기 작업이 많은 대규모 트래픽 환경에서 **성능과 안정성**이 고도로 검증되어 있음

→ 수강 신청 완료나 강의 시작 시점등에 **순간적인 대량 트래픽 발생 가능성**과 **멱등성**(Unique Key 제약조건, 대량 저장등)을 위해 **MySQL** 선택

### 4. WebSocket VS SSE

#### WebSocket: 서버와 클라이언트 간에 1회 연결 후, 계속 유지되는 양방향 통신 채널을 제공하는 프로토콜

- **특징**
    
    **양방향 통신:** 클라이언트가 서버로, 서버가 클라이언트에게 실시간으로 데이터 전송
    
    **헤더 오버헤드 낮음:** 연결이 성립되면 HTTP 헤더 없이 데이터(바이너리, 텍스트)를 주고받아 효율적
    

#### SSE: HTTP 프로토콜을 기반으로, 서버가 클라이언트에게 텍스트 기반의 이벤트를 지속적으로 전송하는 단방향 통신 기술

- **특징**
    
    **단방향 통신:** 오직 서버 → 클라이언트 방향으로만 데이터가 흐름
    
    **단순함 & 자동 재연결:** 표준 HTTP를 사용하므로 구현이 매우 쉽고, 연결이 끊기면 브라우저가 자동으로 재연결을 시도
    

→ **SSE**가 알림 기능 구현에 적합

### 5. SSE만 사용해도 되는가에 대한 의문

단일 서버라면 상관없지만 실제 운영에서는 스케일 업 또는 스케일 아웃 기반 운영 환경 → 단일 서버 형태가 아니라면 **Redis의 Pub/Sub**을 도입하여 Redis가 메시지를 발행하고 Spring boot 서버가 이를 구독하는 형태 설계

## ⚠️ 미구현 / 제약사항

### ✅ 미구현

**선택 구현 전체**

- 발송 스케줄링: 특정 시각에 발송 예약 기능

- 읽음 처리: 여러 기기에서 동시에 읽음 처리 요청이 오면 어떻게 처리할 것인가?
- 최종 실패 알림 보관 및 수동 재시도: 재시도 시 재시도 횟수 초기화 여부를 어떻게 정책화할 것인가?

### ⚠️ 제약사항

- 알림 발송 요청 등록 API는 **테스트 편의성**을 위해 **자기 자신만 알림(로그인 후 응답 결과에 나오는 해당 JWT 토큰(유효시간: 1시간)으로 바로 테스트 가능)**을 보낼 수 있도록 구현되어 있음
- 현재 구조: 알림 발송 요청 등록 API 테스트 시, **중복 방지를 확인**하려면 Request Body에서 “**notificationType”, “userId”, “courseId”** 값을 동일하게 설정하고 요청을 보내야 함(제약조건을 가진 **event_key 컬럼 값: notificationType(REG_COMP_ or REG_CAN_) + userId”_” + courseId**)

→ **notificationType을 Enum으로 구현하고 Notification의 필드로 추가하고 해당 알림 타입을 확인하는 구조로 변경해야 함**
- 현재 구조: Notification 앤티티에 isRead 관련 필드가 없고, **알림 상태(SUCCESS 상태)** 기준으로 **읽음/안읽음을 필터링해서 조회
→ isRead 관련 Enum을 구현하고 Notification의 필드로 추가하여 실제 조회 요청이 발생하면 읽음, 그렇지 않다면 안읽음 상태로 구조를 변경해야 함**
- 현재 구조: **수강신청(In_APP 알림 채널)**, **수강신청 취소(EAMIL 알림 채널)**에 대한 각 알림의 채널이 단순하게 설정되어있음

- 제출 기한 준수를 위한 Readme.md 파일의 가독성 저하
